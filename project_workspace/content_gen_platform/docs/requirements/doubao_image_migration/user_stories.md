## US-01 选择豆包模型并提交文生图请求

**优先级**：P0 | **估算**：M  
**关联 FR**：FR-1、FR-2

**故事**：  
作为一名平台用户，我希望在提交 AI 图片生成请求时能选择具体的豆包 Seedream 模型版本，以便根据速度和质量需求做出权衡。

**验收标准**：

| # | Given | When | Then |
|---|-------|------|------|
| AC-01-1 | 用户已登录，且已在系统设置中配置了有效的豆包 Ark API Key | 用户进入图片生成页面 | 页面展示包含三个选项的模型选择下拉框：Doubao-Seedream-5.0-lite、Doubao-Seedream-4.5（默认选中）、Doubao-Seedream-4.0；页面上不出现任何即梦相关入口或切换开关 |
| AC-01-2 | 用户已选择模型、填写提示词（如"日落时分的海边灯塔"）并点击生成 | 前端发送 POST /api/v1/image/generate/ | 后端在 500ms 内返回 202 Accepted，响应体包含 `request_id` 和 `batch_id` |
| AC-01-3 | 用户已填写提示词，页面中"高级选项"折叠面板处于收起状态 | 用户点击"高级选项"折叠展开 | 面板展开，显示 seed、negative_prompt、guidance_scale 等高级参数输入项（以豆包接口实际支持为准），各参数有合理默认值或空值占位 |
| AC-01-4 | 用户未配置豆包 API Key | 用户点击生成按钮 | 界面显示错误提示"请先在设置中配置豆包 Ark API Key"，不发起生成请求 |
| AC-01-5 | 用户选择了不在枚举列表中的模型名称（通过直接构造请求） | 请求到达后端 | 后端返回 400 Bad Request，错误信息为"不支持的模型版本" |

## US-02 图生图：上传参考图并生成新图片

**优先级**：P0 | **估算**：M  
**关联 FR**：FR-1、FR-3

**故事**：  
作为一名平台用户，我希望能上传一张参考图，并结合提示词生成在风格或内容上与参考图相关的新图片。

**验收标准**：

| # | Given | When | Then |
|---|-------|------|------|
| AC-02-1 | 用户已登录并配置了有效的豆包 API Key | 用户上传一张 JPEG 或 PNG 格式、大小 ≤ 10MB 的参考图，填写提示词并点击生成 | 系统受理请求，返回 202，前端显示生成进度 |
| AC-02-2 | 用户需要精细控制生成结果 | 用户展开高级选项折叠面板，设置 seed 值后提交 | 系统将 seed 参数随请求一并传入豆包 Ark 接口 |
| AC-02-3 | 用户上传了 GIF 或 BMP 格式的图片 | 用户点击生成 | 前端或后端返回明确提示"参考图片仅支持 JPEG 和 PNG 格式" |
| AC-02-4 | 用户上传的图片大小超过 10MB | 用户点击生成 | 返回提示"参考图片大小不能超过 10 MB" |
| AC-02-5 | 图生图任务在 Celery worker 中完成 | 任务执行结束 | 临时参考图片文件已从服务器磁盘清理（tmp 目录下不留残留文件） |

## US-03 生成完成后图片自动入素材库

**优先级**：P0 | **估算**：S  
**关联 FR**：FR-4

**故事**：  
作为一名平台用户，我希望 AI 生成的图片无需我手动操作即可出现在素材库中，以便直接用于内容创作。

**验收标准**：

| # | Given | When | Then |
|---|-------|------|------|
| AC-03-1 | 用户提交了一次图片生成请求 | 豆包 Ark 返回图片 URL，Celery 任务完成 | `media_library` 中自动新增一条 `MediaItem` 记录，`source=ai_generated`、`media_type=image`、`provider=doubao` |
| AC-03-2 | MediaItem 已创建 | 用户进入素材库页面 | 素材库图片列表中可见该图片，缩略图正常加载 |
| AC-03-3 | 生成任务失败（API 报错/超时） | 任务以 failed 状态结束 | 素材库中不产生任何残留的空条目或损坏记录 |
| AC-03-4 | MediaItem 成功创建 | WebSocket 推送 image_completed 事件 | 前端收到推送后，页面中图片状态更新为已完成，可点击查看 |

## US-04 同一次生成的多张图归入同一批次

**优先级**：P0 | **估算**：M  
**关联 FR**：FR-5

**故事**：  
作为一名平台用户，我希望一次生成的所有图片被自动归入同一个批次，以便我能快速找到同一主题的所有生成结果。

**验收标准**：

| # | Given | When | Then |
|---|-------|------|------|
| AC-04-1 | 用户提交一次生成 4 张图片的请求，提示词为"日落时分的海边灯塔"，时间为 2026-05-13 14:30 | 请求被系统受理 | 数据库中创建一条 `ImageBatch` 记录，`total_count=4`，`name` 默认值形如 `0513-1430 日落时分的海边...` |
| AC-04-2 | 4 张图片逐一生成完成 | 每张图片完成时 | 对应 `ImageGenerationRequest` 的 `batch_id` 均指向同一条 `ImageBatch` 记录 |
| AC-04-3 | 所有 4 张图片完成 | 最后一张完成时 | `ImageBatch.status` 更新为 `completed`，`completed_count=4` |
| AC-04-4 | 其中 1 张失败、3 张成功 | 批次所有任务结束 | `ImageBatch.status` 更新为 `partial_failed`，`completed_count=3` |
| AC-04-5 | 用户尝试提交生成 5 张或更多图片的请求 | 请求到达后端 | 后端返回 400 Bad Request，提示"单批次最多生成 4 张图片" |

## US-05 浏览批次列表、重命名批次、删除批次

**优先级**：P1 | **估算**：M  
**关联 FR**：FR-5

**故事**：  
作为一名平台用户，我希望能以批次为单位管理我的图片生成历史，包括重命名批次和删除不需要的批次，以便保持素材库整洁。

**验收标准**：

| # | Given | When | Then |
|---|-------|------|------|
| AC-05-1 | 用户完成了多次图片生成 | 用户进入"生成历史"或"批次管理"页面 | 页面按时间倒序展示批次列表，每行显示：批次名称、模型版本、提示词摘要、图片数量、创建时间 |
| AC-05-2 | 用户点击某批次 | 展开或跳转批次详情 | 批次内所有图片以缩略图网格展示 |
| AC-05-3 | 用户点击批次的"重命名"操作，输入新名称并确认 | PATCH /api/v1/image/batches/{id}/ | 批次名称更新，页面刷新后显示新名称 |
| AC-05-4 | 用户点击批次的"删除"操作，确认弹窗后确认 | DELETE /api/v1/image/batches/{id}/ | 批次记录及批次内所有 ImageGenerationRequest 和对应 MediaItem 均被删除；素材库中对应图片消失 |
| AC-05-5 | 用户尝试删除一个正在生成中（status=processing）的批次 | DELETE /api/v1/image/batches/{id}/ | 后端返回 409 Conflict，提示"批次生成中，无法删除"；前端展示相应错误提示 |

## US-06 历史即梦图片的兼容显示

**优先级**：P1 | **估算**：S  
**关联 FR**：NFR-2  
**决策依据**：OQ-1（完全替换）、OQ-5（历史数据保留原样）

**故事**：  
作为一名平台老用户，我希望在迁移至豆包模型后，之前用即梦生成并保存的图片仍能在素材库中正常显示，不会因为迁移而丢失或显示异常。

**验收标准**：

| # | Given | When | Then |
|---|-------|------|------|
| AC-06-1 | 系统切换至豆包后，历史 `ImageGenerationRequest` 的 `provider` 字段为 null（未迁移） | 用户进入素材库 | 历史即梦图片（`source=ai_generated`）与新豆包图片共存，均可正常展示缩略图，无报错 |
| AC-06-2 | 历史即梦记录未关联任何 `ImageBatch` | 用户进入批次管理页面 | 历史即梦图片不出现在批次列表中（批次列表仅显示豆包生成的新批次） |
| AC-06-3 | 历史即梦图片存在于素材库 | 用户在素材库全局搜索或筛选 | 历史即梦图片可被搜索到，但无"来源：豆包"标签（不强制显示来源，或显示为"未知来源"） |

## US-08 首次使用图片生成的 Key 配置引导（Onboarding）

**优先级**：P0 | **估算**：M  
**关联 FR**：FR-6.1、FR-6.2、FR-6.3、FR-7.1、FR-7.2（均来自 v0.3 补丁）  
**版本**：v0.3 新增（2026-05-14）  
**状态**：APPROVED — OQ-6=B、OQ-7=A、OQ-8=A 已于 2026-05-14 用户 CONFIRM

**故事**：  
作为一名**首次使用** AI 图片生成功能的平台用户，我希望系统在我尚未配置豆包图片生成 API Key 时，能主动提示我需要配置什么、去哪里配置，并在配置完成后无缝引导我回到图片生成页面继续使用，而不是等我提交生成请求失败后才知道需要配置。

**验收标准**：

| # | Given | When | Then |
|---|-------|------|------|
| AC-08-1 | 用户已登录，`doubao_image` 的 `is_configured=false`（从未配置过 Key） | 用户进入图片生成页面（`ImageGeneratorView`）| 页面顶部立即显示 Warning Banner，内容包含"您尚未配置豆包图片生成 API Key，功能暂不可用"，Banner 内有"前往配置"按钮；**Banner 无关闭按钮**（OQ-7=A），将持续展示直到 `is_configured=true`；Banner 不阻止页面其余内容渲染，仅作提示 |
| AC-08-2 | 用户看到 AC-08-1 中描述的 Banner | 用户点击 Banner 中的"前往配置"按钮 | 页面跳转至设置页（`SettingsView`），且"豆包图片生成"Tab 自动激活为当前选中状态；用户无需手动寻找该 Tab |
| AC-08-3 | 用户已跳转至设置页"豆包图片生成"Tab，输入了一个 Ark API Key | 用户点击"测试连接"按钮 | 后端调用 **Ark `/api/v3/models` 接口**（OQ-6=B）验证 Key 有效性（零生图费用，可检测 Key 吊销/欠费），前端展示"连接成功（已自动保存）"或包含具体原因的失败提示（如"Key 无效"、"账号欠费"等）；Key 不以明文出现在提示信息中 |
| AC-08-4 | 用户完成 AC-08-3 的测试（OQ-8=A：**测试成功即自动保存**，无需再次点击保存），`is_configured` 已变为 `true` | 用户点击"前往图片生成"或浏览器返回图片生成页面 | 前端重新查询 `/services/doubao_image/status/` 确认 `is_configured=true`，页面顶部的 Warning Banner **自动消失**（无须用户手动关闭）；用户可直接提交图片生成请求，无需任何额外配置步骤 |
| AC-08-5 | 用户未配置 Key（`is_configured=false`），绕过 Banner 直接点击"生成"按钮提交请求 | Celery 任务因 Key 缺失失败，前端收到 `image_failed` WebSocket 事件 | 前端展示的错误通知中包含可点击的"前往配置"链接（非纯文字），点击后跳转至设置页"豆包图片生成"Tab；错误通知不包含 Key 的任何明文内容 |

**补充说明**：
- AC-08-1 的 Banner 是否允许用户关闭，取决于 **OQ-7** 的决策
- AC-08-3 的测试方式（格式校验 vs. 真实 API 调用），取决于 **OQ-6** 的决策
- AC-08-3/AC-08-4 中"测试"与"保存"的关系（一步 vs. 两步），取决于 **OQ-8** 的决策
