## 一、补丁背景与范围

### 1.1 触发原因

v0.2 批准后，在部署验证阶段发现三处**实施遗漏**（详见 REQ-REVIEW-IMG-001 key_management_review.md）：

1. 前端 `SettingsView.vue` 缺少"豆包图片生成"API Key 配置入口（用户无法在界面上配置 `doubao_image` Key）
2. 后端 `settings_vault/views.py` 的 `_required_keys()` 未包含 `doubao_image` 分支（无必填字段校验）
3. 后端 `_test_connection()` 未包含 `doubao_image` 分支（用户无法测试 Key 连通性）

**后果**：豆包 Seedream 主功能代码已上线（commit `c0506c0`），但用户实际无法配置 Key，功能不可用。

### 1.2 补丁范围

PM 已提出三种方案（A/B/C），用户最终选择**方案 C（独立管理 + 完整 UX 修复）**：保持 `doubao_image` 作为独立 service_type，同时一次性补完所有 UX 缺口，含引导文案说明"可使用与火山引擎 LLM 相同的 Ark Key 值"。

## 二、新增功能性需求

### FR-6 API Key 配置 UX

> **来源**：REQ-REVIEW-IMG-001 缺口 1/2/3；用户拍板选择方案 C（2026-05-14）

#### FR-6.1 设置页"豆包图片生成"独立 Tab

| 字段 | 说明 |
|------|------|
| **需求 ID** | FR-6.1 |
| **需求名称** | 在"设置 → 服务密钥管理"新增"豆包图片生成"Tab |
| **来源** | 用户原始缺陷反馈："用户在界面上没有任何入口来配置 doubao_image 类型的 Key"（REQ-REVIEW-IMG-001 §1.4 缺口 1） |
| **描述** | 前端 `SettingsView.vue` 在现有 Tab 列表（大语言模型、即梦 API、存储设置）之后新增"豆包图片生成"Tab。Tab 内包含：<br>① API Key 输入框（带掩码，类型 password，支持显示/隐藏切换）<br>② **"测试连接"按钮**（调用 `POST /api/v1/users/me/services/doubao_image/test-and-save/`）<br>③ 引导文案（见 FR-6.2）<br><br>**【OQ-8=A 已决】测试即保存，无独立 Save 按钮**：点击"测试连接"后，后端原子执行验证并保存 Key，成功则直接生效；前端不展示独立的"保存"按钮（避免两步操作）。若测试失败，Key 不写入数据库。 |
| **约束** | Tab 位置：建议紧跟"大语言模型"Tab 之后，因二者同属 Ark 体系；具体位置由前端开发自行判断，符合视觉分组逻辑即可 |
| **验收要点** | 用户可在该 Tab 输入 Key、点击"测试连接"后自动保存；已保存时显示掩码（如 `ark-***`）而非明文；页面无独立"保存"按钮 |

#### FR-6.2 配置页引导文案

| 字段 | 说明 |
|------|------|
| **需求 ID** | FR-6.2 |
| **需求名称** | "豆包图片生成"Tab 展示 Key 复用引导文案 |
| **来源** | 用户选择方案 C；REQ-REVIEW-IMG-001 §四 推荐理由 |
| **描述** | 在 FR-6.1 Tab 内的 API Key 输入框下方，展示以下引导文案（或语义等效措辞）：<br>**"豆包图片生成使用独立 Key，以便单独管理配额和账单。若您已在"大语言模型 — 火山引擎"中配置了 Ark Key，可在此处填写相同的值。"** |
| **约束** | 文案为静态展示，不自动读取或预填充 `llm_volcano` 的 Key 值（避免后端实现"克隆接口"的额外复杂度）；不实现"一键复制"按钮 |
| **验收要点** | 文案在 Tab 内可见，措辞明确说明"独立但可填相同值"，不引起用户困惑 |

#### FR-6.3 后端 `doubao_image` 连接测试接口

| 字段 | 说明 |
|------|------|
| **需求 ID** | FR-6.3 |
| **需求名称** | `_test_connection()` 支持 `doubao_image` 分支 |
| **来源** | REQ-REVIEW-IMG-001 §1.4 缺口 3 |
| **描述** | `apps/settings_vault/views.py` 的 `_test_connection()` 函数新增 `doubao_image` 处理分支。**【OQ-6=B 已决】**：使用用户提供的 Key，调用 Ark 非生图接口 **`GET https://ark.cn-beijing.volces.com/api/v3/models`**（模型列表接口），通过 HTTP 响应状态验证 Key 的真实有效性（含吊销、欠费等场景），零图片生成费用。**【OQ-8=A 已决】**：测试通过后立即原子写入加密 Key，通过 `POST /api/v1/users/me/services/doubao_image/test-and-save/` 端点一步完成。测试失败时不写入数据库，返回包含具体原因的错误信息。 |
| **约束** | 测试不可在 `_required_keys()` 校验通过前执行；Key 不得出现在响应日志的明文字段中；响应体不得包含 Key 值或 Key 前缀 |
| **同步变更** | `_required_keys()` 需同步新增 `"doubao_image": ["api_key"]` 分支，确保 `api_key` 为必填项、空值时后端返回 400 |
| **验收要点** | 用户在 FR-6.1 Tab 中点击"测试连接"后，后端调用 Ark `/api/v3/models` 接口验权；前端展示"连接成功（已自动保存）"或包含具体原因（如"Key 无效"、"账号欠费"）的失败提示；成功时 Key 已持久化，无需再次点击保存 |

### FR-7 错误提示与预检

> **来源**：REQ-REVIEW-IMG-001 §3.3；用户拍板选择方案 C（2026-05-14）

#### FR-7.1 图片生成页面"未配置 Key"预检 Banner

| 字段 | 说明 |
|------|------|
| **需求 ID** | FR-7.1 |
| **需求名称** | 图片生成页加载时展示"未配置 Key"预检 Banner |
| **来源** | REQ-REVIEW-IMG-001 §3.3 问题 3；用户方案 C 选择 |
| **描述** | `ImageGeneratorView.vue` 页面**加载时**（`onMounted`）调用 `GET /api/v1/users/me/services/doubao_image/status/` 接口，检查响应中的 `is_configured` 字段。若该字段为 `false`（或该条目不存在），在页面顶部展示一条 Warning Banner，内容为："您尚未配置豆包图片生成 API Key，功能暂不可用。"，Banner 内含"前往配置"按钮，点击后跳转至 `SettingsView` 并自动激活"豆包图片生成"Tab。 |
| **Banner 显示/隐藏规则** | **【OQ-7=A 已决】常驻显示，无关闭按钮**：Banner 持续展示，直到后端返回 `is_configured=true` 后自动消失（前端完成配置跳回时重新查询状态）；不提供"稍后配置"或任何关闭操作 |
| **不依赖任务失败** | Banner 为前端主动预检，不依赖 Celery 任务执行失败后的 WebSocket 推送来感知未配置状态 |
| **验收要点** | 未配置 Key 时进入图片生成页面，Banner 立即可见；点击"前往配置"可跳转至设置页对应 Tab |

#### FR-7.2 任务失败错误消息含可点击跳转链接

| 字段 | 说明 |
|------|------|
| **需求 ID** | FR-7.2 |
| **需求名称** | 图片生成失败时错误提示含可点击"前往配置"链接 |
| **来源** | REQ-REVIEW-IMG-001 §3.3 问题 1/2；用户方案 C 选择 |
| **描述** | 当前端收到 `image_failed` WebSocket 事件，且事件的 `error` 字段内容包含"未配置"或"API Key"相关信息时，前端将纯文字提示升级为带操作链接的通知组件（如 `ElNotification` with action button），展示"前往配置"可点击按钮，点击后跳转至 `SettingsView` 的"豆包图片生成"Tab。 |
| **约束** | 仅在错误内容明确指向 Key 未配置时触发升级提示；其他类型的任务失败（如 API 超时、内容审核拒绝）继续使用现有错误提示组件 |
| **验收要点** | 用户在未配置 Key 时提交生成请求，收到的错误通知中包含可点击的"前往配置"链接；链接点击后跳转至正确 Tab |

## 三、非功能性需求（本补丁无新增 NFR）

FR-6 / FR-7 的实现遵循 v0.2 已定义的 NFR-2（可用性）和 NFR-3（安全性/API Key 管理）规范，无需新增 NFR 条目。

具体说明：
- FR-6.1 的 Key 存储继续使用 AES-256-GCM 加密（NFR-3）
- FR-6.3 的测试接口调用 Key 不得出现在日志明文（NFR-3）
- FR-7.1 的预检接口调用失败（如 settings API 不可达）时，Banner 应降级为"无法检测配置状态，请手动确认"或不显示，不导致页面崩溃（NFR-2）

### ADR-06 补充决策说明

**背景**：v0.2 中 ADR-06 在"影响"一节判断"settings_vault 视图/序列化器无需新增，现有通用 CRUD 接口已支持任意 service_type"，该判断低估了前端 SettingsView 需要同步新增配置 Tab 的工作量，导致实施阶段遗漏前端配置入口。

**追加决策（2026-05-14，方案 C）**：

| 追加约束项 | 决策说明 |
|-----------|---------|
| **独立 service_type 隔离** | 保持 `doubao_image` 作为独立 service_type，不与 `llm_volcano` 合并。理由：Ark LLM 调用依赖 Endpoint ID（`ep-xxxxxxxx`），而图片服务不需要；若合并 service_type，需在 `tasks.py` 中解析 `llm_volcano` JSON 提取 `api_key`，且当用户未配置豆包 LLM 时图片服务无法工作，耦合带来的复杂性超过收益。 |
| **配额与账单隔离** | 两个独立 service_type 实现了 LLM 和图片生成的配额/账单逻辑隔离，支持为两类服务分别设置用量告警和 Key 轮转策略。 |
| **UX 层面允许复用相同 Ark Key 值** | 技术上，同一个 Ark API Key 可同时调用 LLM 端点和图片端点（均属 Ark API v3）。因此，UX 层面通过引导文案（FR-6.2）明确告知用户"可在此处填写与火山引擎 LLM 相同的 Key 值"，降低配置摩擦，同时保持后端两条独立的查询路径。 |
| **前端实施边界** | 选择独立 service_type 后，前端 SettingsView.vue 必须新增对应配置 Tab（FR-6.1），这是已知必要实施工作，不可省略。 |
